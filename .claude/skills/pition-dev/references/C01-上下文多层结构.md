# C01 上下文多层结构

数据快照：**v0.7.0**（v0.7.0 只新增 `scripts/new-extension.mjs` 脚手架，注入分层与内容未变）。
源码：`src/injection/`（机械）+ `src/role.ts` / `src/role-mode.ts` / `src/scene.ts` /
`src/sop.ts` / `src/prompt-state.ts` / `src/fields.ts`（领域） /
`@earendil-works/pi-coding-agent/dist/core/system-prompt.js`。

## 1. pi 的 9 层 system prompt（渲染顺序固定）

| 层 | 内容 | 默认值 | pition 是否动过 | 在哪改 |
| --- | --- | --- | --- | --- |
| **preamble** | 角色定位 | `"You are an expert coding assistant operating inside pi..."` | **不动**——碰了就改 agent 身份，prompt cache 也 miss | 不动 |
| **tools** | 可用工具清单（按 `selectedTools` 过滤 + `promptSnippet`） | 自动渲染 | **加了 snippet**（v0.5.0 起 7/7 覆盖） | 各 tool 的 `promptSnippet` |
| **rules** | 行为准则（默认 2 条 + `toolGuidelines` + `promptGuidelines`） | 自动渲染 | **改了**：3 条全局 guideline + 按场景裁剪 tool guideline | `role.ts#GLOBAL_GUIDELINES` + `pruneToolGuidelines` |
| **docs** | pi 文档索引 | 14 个 .md 链接 | 不动 | 不动 |
| **addendum** | 用户配置追加 | settings.json `appendSystemPrompt` | 不动 | 用户配置 |
| **project_context** | AGENTS.md / CLAUDE.md | 从 cwd 向上找 | 不动 | 用户配置 |
| **skills** | 已加载 skill 的发现条目（name + description + location） | 自动渲染 | **被动计入台账**（3 个 skill 的常驻发现成本） | `skills/*/SKILL.md` |
| **cwd** | 当前工作目录 | `process.cwd()` | 不动 | 不动 |
| **[custom]** | `sections[name]` | 无 | **改了**：`pition_core` / `pition_scene` / `pition_fields` / `pition_runtime` / `pition_goal` / `pition_span` | `role.ts` + `role-mode.ts` |

源码锚点：`system-prompt.js` — `buildPromptSections()` / `buildRules(selectedTools, toolGuidelines, promptGuidelines)`。

## 2. pition 的注入分层（v0.5.0，v0.6.0 起机械部分搬到 `src/injection/`）

> **v0.6.0 分层：机械 vs 领域**。与 pition 领域无关的机械（宿主探测、片段求值、场景路由、
> 分层装配、结果回流、足迹裁剪、字节度量、一轮编排）在 **`src/injection/`**（整目录可复制到
> 别的扩展复用，`src/injection/README.md`）；本文件讲的**注入位置与内容不变**，只是实现搬了家。
> 编排现在是 `createInjectionRuntime(spec, state)`（`src/injection/runtime.ts`），
> `src/role-mode.ts` 只填领域插槽（`buildState` / `build` / `runtimeSections` / `fallback`）。

一轮 `before_agent_start`（`src/role-mode.ts`）只读一次 cfg，然后：

```
event.prompt（用户原话）
   └─ routeScene(prompt, prevScene)            ← src/scene.ts（优先级 setup>train>recall>log>chat，带粘性）
        └─ buildPromptState(...)               ← src/prompt-state.ts（时刻/时段/目标/字段覆盖/会话事实）
             └─ buildRoleInjections(cfg, scene, state)   ← src/role.ts
                  ├─ pition_core    恒定：库标签 + 工具索引 + 3 条硬边界
                  ├─ pition_scene   场景：**按 state 装配的片段**（src/sop.ts，fragment.when(state)）
                  ├─ pition_fields  事实：当前库字段字典（src/fields.ts，带预算截断）
                  ├─ pition_runtime 易变：现在几点 + 本会话写入 + 上一轮失败/警告
                  └─ toolGuidelines 裁剪：不相关 tool 的 guideline 置空（chat 不裁剪）
   └─ （独立于助理模式）pition_span / pition_goal：有数据即注入
```

| 注入位置 | 时机 | 内容 | 来源 |
| --- | --- | --- | --- |
| `promptGuidelines.push`（rules 层） | 助理模式开 | 3 条全局准则（边界判断 / 情绪也算事实 / 不主动列 page） | `role.ts#GLOBAL_GUIDELINES` |
| `event.systemPromptOptions.toolGuidelines[name] = []` | 助理模式开 | 把本场景白名单外的 tool guideline 摘掉（**只改文本**） | `role.ts#pruneToolGuidelines` |
| `sections.pition_core` | 助理模式开 | 库标签 / 工具索引 / 硬边界 / 未绑定库时的「去配置」指路 | `role.ts#renderCore` |
| `sections.pition_scene` | 场景 ≠ chat | 开场行 + **命中的片段**（每段 1-3 行，按本状态成立才出现） | `sop.ts#renderScene` |
| `sections.pition_fields` | 需写属性的场景 + 已绑库 | 可写字段 `名(type=append语义)：说明`，超预算截断 | `fields.ts#renderFieldDict` |
| `sections.pition_runtime` | 助理模式开 | 现在（日期/星期/时刻/时段）+ 本会话已写入 N 条 + 上一轮失败/警告 | `prompt-state.ts#renderRuntimeSection` |
| `sections.pition_goal` | 有今日 goal | 目标 + 逐条 x/target + 总百分比 + ⚠️ 断更提示 | `goal.ts#renderGoalsStatus` |
| `sections.pition_span` | 有进行中 span | 事件名 + 备注 + 已持续时长 + 开始时刻 | `span.ts#renderSpansStatus` |

**关键观察 1**：**只有恒定事实常驻**。场景片段、字段字典随场景与状态出现/消失——「无关内容不占 token」。

**关键观察 2**：**SOP 是状态驱动的片段，不是固定长文**（v0.5.0 第二版修的病：用户反馈「提示词很容易
变得静态」）。`SopFragment.when(state)` 决定要不要出现，`text` 可以是函数以插入真实数字
（如「下一项是『俯卧撑』（2/4 轮）」）。同一场景在不同状态下注入的片段集完全可能不相交。

**关键观察 3**：**易变层单独成段**。`pition_runtime` 每轮都变（时间分钟级），不能与 SOP 挤在一个
section 里——否则稳定内容也跟着每轮重刷 cache。

**关键观察 4**：**工具集永不改变**。`pruneToolGuidelines` 只清文本；能力不做场景门禁（见 B01 §6.4 的血债）。

**关键观察 5**：**运行时事实与助理模式无关**。span/goal 是「现在几点、用户在干嘛」，关了助理模式也注入。

**关键观察 6**：**tool 结果回流**。`tool_execution_end` 采集进 `SessionFacts` → 下一轮进易变层 +
驱动片段选择（例如 write 报过「没有 page」才出现逃生口片段）。

**关键观察 7**：**字段说明终于进视野**。此前 `fields[].description` 只用于算覆盖率，agent 想写属性
必须多一次往返猜字段名——这是「上下文不准确」最典型的一处。

## 3. 决策树：往哪层注入？

```
我想让模型看到 X
├─ X 是「你是什么」（agent 身份） → preamble（不推荐——cache miss）
├─ X 是「行为准则 / 不要做 Y」（≤3 条、任何场景都成立） → rules（promptGuidelines.push）
├─ X 是「恒定事实」（库名、工具索引、硬边界） → sections.pition_core
├─ X 是「某场景下的对策，且分状态」 → src/sop.ts 的片段（带 when）
├─ X 是「每轮都变的事实」（时间、本会话进度、上一轮结果） → sections.pition_runtime
├─ X 是「当前库字段」 → sections.pition_fields
├─ X 是「某个 tool 自身机理」（怎么调、参数语义） → 该 tool 的 promptGuidelines（≤3 条）
├─ X 是「完整流程 / 对话示例 / 排查表」 → skills/*.md（on-demand，模型按需读）
├─ X 是「可用工具列表」 → promptSnippet（每个 tool 一行）
├─ X 是「项目特定上下文」 → project_context（写 AGENTS.md）
└─ X 是「用户全局追加」 → addendum（settings.json 的 appendSystemPrompt）
```

**核心规则**：

- **不要动 preamble**；**永不写 `forceSystemPrompt`**（整段替换 = cache 全 miss）
- **`promptGuidelines` 只放 bullet 短句**（≤3 行），长段放 `sections[name]`
- **恒定 / 场景 / 易变 三分**：把「会变的」与「不常变的」放进不同 section，别让易变内容拖累 cache
- **新增能力时先问「这是常驻、场景、还是按需」**：常驻 = 每轮都付 token；按需 = 写进 skill

## 4. cache 行为（关键）

`diffSystemPromptSections(previous, current)`：逐 turn diff ——
相同 section 不刷 cache；变化/缺席的 section 才产生 transcript delta（缺席 → patch 为 `null` = 移除）。

**实际含义**：

- `pition_core` 内容稳定 → 首轮注入后长期 cache hit
- `pition_scene` 只在**场景切换或状态跃迁**（如目标建好/断更）那一轮产生 delta——片段化的副作用
  是「状态一变就 diff」，但换来的是内容永远贴合当下；粘性路由负责减少无谓的场景切换
- `pition_runtime` / `pition_goal` / `pition_span` 带实时数字（now 每次都变）→ 每轮 delta，
  只能取舍（这是刻意的：用户要知道"现在几点、进度多少、已经跑了多久"）
- mutation **不写回** `_baseSystemPromptOptions`：每轮从 base 复制一份 → 上轮的 scene/fields
  不会残留（缺席即 patch null），无需手动清理

## 5. 注入预算门禁（v0.5.0，对齐 pi-dynamic-workflows 的 `context:check`）

```
npm run context:generate   → 重新生成 docs/context-budget.json（改了注入面就跑）
npm run context:check      → 校验台账是否漂移 + 是否超上限（已并入 npm run check）
```

台账度量 5 个面（`src/context-budget.ts`，纯函数）：

| 面 | 含义 |
| --- | --- |
| `globalGuidelines` | 3 条全局 guideline 的字节 |
| `toolGuidelines` | 7 个 tool 的 guideline 合计（**最坏情况 = chat 不裁剪**） |
| `toolDefinitions` | `JSON.stringify({name, description, parameters})` + snippet 行 |
| `skillsDiscovery` | 每个已注册 skill 的发现条目（照 pi 的 `formatSkillsForPrompt` 逐字符对齐） |
| `sceneInjections` | **15 个「场景 × 状态」组合**的 section 字节 + 该组合**实际出现的片段 id** + 保留的 tool guideline 字节 |

- 上限常量在 `src/context-budget.ts#BUDGET_CEILINGS`（含 `runtimeBytes` 易变层单段上限），超限报人类可读的违规说明
- 度量用**固定 fixture**（库 / 时刻 / 会话事实），不随本机配置与时钟漂移
- 台账必须提交；漂移 = check 失败 → 逼作者显式确认「这次涨了多少、值不值」

## 6. 宿主兼容与降级（v0.5.0 工程化）

`sections` / `toolGuidelines` 是 **pi 0.86 才有的**（实测：0.85 的 `BuildSystemPromptOptions` 里没有这两个字段）。
所以注入前必须先探测（`src/injection/host.ts#supportsStructuredInjection`）。下界常量在
`src/injection/version.ts#MIN_PI_FOR_STRUCTURED`（`"0.86.0"`，package.json 的 peer 与 CI 都读它）：

| 情形 | 行为 |
| --- | --- |
| 宿主支持（≥0.86） | 正常分层注入 + tool 足迹裁剪 |
| 宿主不支持（≤0.85） | **整体跳过**结构化注入 + `ctx.ui.notify` 提示一次（每个会话一次）；工具调用照常可用 |
| 装配/渲染抛错（配置被改坏等） | 降级为最小 `pition_core`（含「装配失败」提示），不写半成品 section |

上表三种情形 + 「先构造后落地」都由 `src/injection/runtime.ts#createInjectionRuntime` 统一实现。

三条不变量：

1. **先构造后落地**：本轮要注入的内容全部算完（可能在 `buildRoleInjections` / `renderGoalsStatus` 抛错）
   才写进宿主的 options——避免「部分注入」的半成品状态。
2. **不创建宿主没声明的字段**：旧宿主没有 `toolGuidelines` 就不写它（凭空创建不会被渲染，只会更难排障）。
3. **静默零注入是必须消灭的故障形态**：它不报错、看起来像「模型不听话」。能力探测 + 降级 + 真宿主校验
   三件事都是为了让它变成「可见的提示」。

**真宿主校验**（`test/host-injection.test.ts`）用 pi 真实的 `discoverAndLoadExtensions` + `ExtensionRunner`
跑 `before_agent_start`，断言三件只有真宿主能验的事：写入是否被宿主采纳、裁剪是否经真实合并生效、
同状态连续两轮的 options 是否深度相同（＝ section diff 为空 ＝ 稳定层真的不刷 cache）。
排障用 `node scripts/dev/diag-injection.mjs "<用户原话>"` 直接看这一轮注入了什么。

## 7. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| `forceSystemPrompt = "..."` | 整段 prompt prefix 失效，cache miss | 永远不写 |
| **SOP 写成固定长文**（`when` 全缺省） | 一半内容是当下不成立的（教怎么建已建好的目标）= 噪音 + 误导 | 片段化 + `when(state)`；文案可为函数以带真实数字 |
| **易变内容混进稳定 section** | 稳定内容也跟着每轮刷 cache | 易变只放 `pition_runtime`（另有 `runtimeBytes` 上限） |
| 易变层里写建议 | 与场景片段重复注入 | 易变层只放事实，建议归片段 |
| 往 `promptGuidelines` 写长段 / 写满十几个 tool 的准则 | rules 层变大且每轮都付 | ≤3 条全局 + 每 tool ≤3 条；场景化内容进 `sop.ts` |
| 用 `setActiveTools` 摘掉工具 | agent 需要时无路可走 | 只裁 guideline 文本 |
| 把 skill 全文堆进 section | 单 section 过大 | 浓缩进 `sop.ts`，完整版留 `skills/*.md` |
| 在 preamble 里塞 pition 角色定位 | 失去 pi 默认 preamble | 放 `sections.pition_core` |
| 改了注入面不刷新台账 | `npm run check` 红 | `npm run context:generate` |
| **不探测宿主就写 `sections`** | 旧宿主每轮抛错 → 被错误边界吃掉 → 静默零注入 | `supportsStructuredInjection()` + 提示一次 |
| **先写再算**（注入过程中途抛错） | 半成品注入了（core 有、剧本没有），更难判断 | 先全部构造，再一次性落地 |

## 8. 加新注入点的流程

1. 先按 §3 决策树决定注入到哪一层
2. 恒定内容 → `role.ts#renderCore`；场景对策 → `src/sop.ts` 的**片段**（带 when）；
   每轮都变的 → `src/prompt-state.ts`（先扩 `PromptState`，再在 `renderRuntimeSection` 里渲染）
3. 新场景 → 在 `scene.ts` 加触发正则 + `sop.ts` 加片段 + `test/scene.test.ts` / `test/sop.test.ts` 加用例
4. **不要新增 section 名**（越少越好）；确实需要时同步更新本文件 §2 表
5. `npm run context:generate` + `npm run check`
6. 观察下一轮请求的 transcript delta（确认不是 cache miss 风暴）
