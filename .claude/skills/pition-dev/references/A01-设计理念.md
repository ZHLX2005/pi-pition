## 核心理念（一句话）

> **pition = Notion 个人记录助手的 agent =「web 引导配置 + agent 内核识别写入」双形态。配置是一次性引导，最终沉淀为运行态 tool；agent 内核只负责一件事：在对话里识别用户今日记录内容（含区间事件与每日目标），自动写到指定 db 的最新 page。**

两个角色：
- **引导态**：把"我能跑的 agent 到 notion 数据库"这条流程做顺 — token → 选库 → 看结构 → 补字段说明 → 开助理模式
- **运行态**：agent 拿到绑定上下文后，运行态 tool 完成「识别 → 写入 → 区间事件 → 每日目标」全流程

## boot 元工具 5 阶段契约

产品 idea 里规划的"渐进式 boot 元工具"是引导态的**统一入口**。一次完整 boot 走 5 步（token → select_db → describe_fields → set_mode → done），每步都可独立中断 / 回访：

| 阶段 | 用户动作 | 系统动作 | 可中断？ |
|---|---|---|---|
| **1. token** | 填 Notion integration token | `GET /v1/users/me` 实时校验，落盘 | 中断 → 不落盘 |
| **2. select_db** | 从可访问库列表里选 1 个（切空间也走这里） | 列出所有可见库 + 字段数，已绑定的标注 `[已描述过：覆盖率]` | 中断 → 不落盘 |
| **3. describe_fields** | 一次性提交字段说明数组（或只查看覆盖率） | 拉库 schema 过滤计算字段 → 写入 `pition.config.json` | 中断 → 整次不保存 |
| **4. set_mode** | 开关助理模式（等价 `/pition-mode`） | 落盘 `_assistantMode` | 落盘即生效 |
| **5. done** | 查现状 | 返回 token / 当前库 / 字段覆盖率 / 助理模式 | — |

### 阶段 3 的特殊性：渐进式回访

`describe_fields` 是**唯一可以单独回访**的阶段：
- 用户改 token → 走阶段 1
- 用户换库 / 加库 → 走阶段 2
- 用户**只改某几个字段的 description** → 直接走阶段 3（不重走 1-2），允许部分提交

这是「渐进式」的核心：**配置不再是一次性事务，而是可增量优化的过程**。

### 落盘时机：两阶段提交

`stage=token` 只写 token（bindings 为空也落盘）→ 会话中断也不丢；`select_db` 再补上库与字段类型；
`describe_fields` 边填边补。所以配置状态是**三维度**而不是二分：
「token 有 / 库选了 / 字段覆盖率 X%」。

## 工具事件的载体（运行态）

**7 个 tool 在工厂里无条件注册**（不依赖配置是否就绪），未选库时由各 tool `execute` 首行的 `currentBinding()` 抛错并指引 agent 去 `pition_boot`。运行态的核心约束：

1. **写入默认到最新 page** — `pition_write` 是日常主路径（今天的记录默认往最新一条追加/合并属性，不是每次新建）
2. **字段 description 是 agent 唯一的"字典"** — 配置里的字段 description 由**每轮注入的 `pition_fields` 段**交给 agent（v0.5.0 起；此前它只被用于算覆盖率，等于死数据）。`pition_boot stage=done` 只给覆盖率与状态，不给字段名
3. **agent 内核只填简单值** — title/rich_text/select/date 等标量；`toNotionProperty()` 负责转 Notion API 格式
4. **计算字段不可写** — formula/relation/rollup 在 `WRITABLE_TYPES` 白名单之外，永远不能写入

## 为什么是"元工具 + 运行态 tool"而不是直接注册运行态 tool

| 维度 | 直接注册 6 tool（被否） | 元工具 + 运行态 tool（采纳） |
|---|---|---|
| 配置时机 | 工厂启动时读 config 做注册门禁（配置在会话中现配 → 工具缺失，必须 /reload） | 全部无条件注册，校验下沉到 execute 首行；引导态可独立中断、回访、增量 |
| 错误兜底 | 只有 boot 可见 + 其余静默缺失（用户不知道该怎么办） | 全部注册，未配置时错误信息主动指引去 `pition_boot`；`/pition` 命令始终可达 |
| 字段迭代 | 改 config → 重启 pi | 改字段 description → 下一轮对话立即生效（注入面每轮重读 cfg） |
| 用户体感 | "这插件没反应" | "我跟着几步就能跑起来" |

**核心区分**：引导态 vs 运行态必须分离，否则引导态的任何中间态都会污染运行态（half-config 让 agent 写入时崩溃）。

## 关于 web 页面（idea 远期目标）

产品 idea 里提到的"web 页面进行 tool 设置"目前**未实现**，仅在 nx-as 物化路径（`install.mjs`）里承担 token 注入。本 ref 仅记录设计意图：

- web 页面应复用 `src/config.ts` / `src/databases.ts` 的纯函数（`loadConfig / saveConfig / fetchFields`，不依赖 pi runtime）
- web 页面落盘后，pi 端下一轮请求即生效（注入面与 tool execute 都重读 cfg）
- UI 流程可与 TUI 向导同构（页面即 5 阶段向导的可视化版）

落地时再起具体 ref，本节不展开。
