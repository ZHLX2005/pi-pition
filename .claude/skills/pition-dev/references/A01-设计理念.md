## 核心理念（一句话）

> **pition = Notion 个人记录助手的 agent =「web 引导配置 + agent 内核识别写入」双形态。配置是一次性引导，最终沉淀为 4 个 tool；agent 内核只负责一件事：在对话里识别用户今日记录内容，自动写到指定 db 的最新 page。**

两个角色：
- **引导态**：把"我能跑的 agent 到 notion 数据库"这条流程做顺 — token → 选库 → 看结构 → 补字段说明 → 保存 → tool 注册
- **运行态**：agent 拿到绑定上下文后，4 个 tool 即可完成「识别 → 写入」全流程

## boot 元工具 4 阶段契约

产品 idea 里规划的"渐进式 boot 元工具"是引导态的**统一入口**。一次完整 boot 走 4 步，每步都可独立中断 / 回访：

| 阶段 | 用户动作 | 系统动作 | 可中断？ |
|---|---|---|---|
| **1. token** | 填 Notion integration token | 实时校验，显示工作区名 | 中断 → 不落盘 |
| **2. 选库** | 从可访问库列表里选 1 个或多个 | 列出所有可见库 + 字段数，已绑定的标注 `[已绑定]` | 中断 → 不落盘 |
| **3. 加载字段** | （系统自动） | 拉库 schema，过滤掉 formula/relation/rollup 等计算字段 | — |
| **4. 补字段说明** | 逐字段填 description（已配过的字段显示原说明，回车沿用） | 写入 `pition.config.json` | 中断 → 整次不保存 |

### 阶段 4 的特殊性：渐进式回访

阶段 4 是**唯一可以单独回访**的阶段：
- 用户改 token → 走阶段 1
- 用户换库 / 加库 → 走阶段 2
- 用户**只改某一个字段的 description** → 直接走阶段 4（不重走 1-3）

这是「渐进式」的核心：**配置不再是一次性事务，而是可增量优化的过程**。

### 落盘时机：两阶段提交（设计目标）

当前实现是"一次会话必须配完整才能保存"（cancel = 整次放弃）。产品 idea 要求的两阶段：

```
阶段 1+2（连接 + 选库）落盘 → token + 空 bindings → ctx.reload()
阶段 4（字段描述）边填边补 → 写库字段 → 累计覆盖率 → notify "覆盖率 N/M"
```

这样配置状态从「未配置 / 已配置」二分，变成「token 有 / 库选了 / 字段覆盖率 X%」三维度。

## 工具事件的载体（运行态）

一旦引导态结束，4 个 tool 即向 agent 注册（见 SKILL.md「Tool 一览」）。运行态的核心约束：

1. **写入默认到最新 page** — `pition_update_latest` 是日常主路径（今天的记录默认往最新一条追加，不是每次新建）
2. **字段 description 是 agent 唯一的"字典"** — 配置里的字段 description 原样进 `pition_stores` 返回，agent 靠这段文字理解"每个字段该填什么"
3. **agent 内核只填简单值** — title/rich_text/select/date 等标量；`toNotionProperty()` 负责转 Notion API 格式
4. **计算字段不可写** — formula/relation/rollup 在 `WRITABLE_TYPES` 白名单之外，永远不能写入

## 为什么是"元工具 + 4 个 tool"而不是直接注册 4 个 tool

| 维度 | 直接注册 4 tool（被否） | 元工具 + 4 tool（采纳） |
|---|---|---|
| 配置时机 | 工厂启动时一次性读 config，缺失即静默退出 | 引导态可独立中断、回访、增量 |
| 错误兜底 | 0 工具 + 0 报错（用户不知道该怎么办） | `/pition` 引导态始终可达，命令无条件注册 |
| 字段迭代 | 改 config → 重启 pi | 改字段 description → `ctx.reload()` 热重载 |
| 用户体感 | "这插件没反应" | "我跟着 4 步就能跑起来" |

**核心区分**：引导态 vs 运行态必须分离，否则引导态的任何中间态都会污染运行态（half-config 让 agent 写入时崩溃）。

## 关于 web 页面（idea 远期目标）

产品 idea 里提到的"web 页面进行 tool 设置"目前**未实现**，仅在 nx-as 物化路径（`install.mjs`）里承担 token 注入。本 ref 仅记录设计意图：

- web 页面应复用 `extensions/pition.ts` 里的 `loadConfig / saveConfig / fetchFields` 纯函数（不依赖 pi runtime）
- web 页面落盘后，pi 端通过热重载生效
- UI 流程可与 TUI 向导同构（页面即 4 阶段向导的可视化版）

落地时再起具体 ref，本节不展开。
